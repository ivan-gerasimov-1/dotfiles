## Стилистические правила

### С1. Что НЕ переводить — оставлять как термин

Технические идентификаторы и имена собственные не переводятся. Перевод затрудняет чтение и рвёт связь с кодом. Сюда входят:

- имена сущностей кода (агрегаты, классы, поля, перечисления, методы, очереди), в формате кода;
- названия модулей продукта, фич и технологий;
- аббревиатуры разработки и термины предметной области;
- устоявшиеся термины команды, в том числе гибриды (исключение из §С2 и §С3).

Конкретные списки лежат в [glossary.md](glossary.md). Термин, которого там нет, но который по контексту устоялся и не имеет нормального русского эквивалента, оставь как есть и назови в отчёте кандидатом в глоссарий. Англицизм с нормальным русским эквивалентом идёт по §С2. Если у термина из глоссария появится явный русский эквивалент в командной речи, глоссарий надо обновить.

### С2. Англицизмы без технической нагрузки — заменять

Слово надо заменять, если у него есть нормальный русский эквивалент, оно НЕ имя класса/модуля/технологии и не входит в исключения §С1. Правило действует и в заголовках, например «Single write point» → «Единая точка записи», «Runtime-ветвления» → «Ветвления во время выполнения». Типовые замены:

| Англицизм | Замена |
|---|---|
| additive (изменения) | «только добавляют поля», «не ломают существующие документы» |
| rolling-deploy safe | «безопасно при постепенной выкатке» |
| shared (слой/поле) | «общий (слой/поле)» |
| submit (в свободном тексте) | «отправка формы» |
| scope | «входит в этот документ» / «объём» |
| single write point | «единая точка записи» |
| bootstrap (в свободном тексте) | «начальная конфигурация» |
| case-ветка, case-branch | «ветка для значения X», «явная ветка» |
| compile-time / runtime | «на этапе компиляции» / «во время выполнения» |
| type narrowing | «сужение типа» |
| deliverability | «доставка» |
| user-facing | «пользовательский» |
| консьюмеры | «потребители» |
| populated (виджет, поле) | «загружен», «подгружен», «разрешён» |
| persistнутый | «сохранённый» |
| payload (события) | «тело сообщения» |

Замены, принятые для терминов продукта, лежат в [glossary.md](glossary.md).

### С3. Гибриды русского и английского недопустимы

Гибрид заменяется чистым русским словом или чистым английским термином в формате кода. Для части гибридов готовая замена есть в таблице §С2. Примеры: `сабмитнуть`, `дискардить`, `дроп-нуть`, `комит-нуть`, `sync-пайплайн`, `runtime-свитч`, `submit-форма`, `widget-сессия`, `checkout-конфиг`, `payment-сессия`, `UI-механики`.

Окончания и приставки нельзя клеить к английским корням, если есть русское слово. Прилагательное-приставка «english-кириллица» через дефис почти всегда плохо. Исключение составляют гибриды из исключений §С1 (`lazy-чанк`, `pledge-кампания`).

### С4. Грамматика и пунктуация

- **«и так далее» вместо «...» в скобках.** Лучше «(миграции, upsell, Virtual Terminal и так далее)», чем «(миграции, upsell, Virtual Terminal, ...)». Многоточие допустимо в таблицах для краткости.
- **Двоеточие в коротких метках и метаданных.** «Предусловие: 3.1», «Расширяется: поле `isPledge`». В прозе меток нет, там действует §С12.
- **Согласование при сложных подлежащих с кодом.** `Subscription` мужского рода (документ, агрегат), `Widget` мужского рода, `Charge` мужского рода. Проверять окончания, например «создаётся `Subscription`», «существующий `Charge`».
- **Дефис vs тире.** Если тире уместно (определение термина по §С12), это длинное тире (`—`). Дефис только в составных словах и в гибридах из глоссария («pledge-кампания»).

### С5. Структура и стиль предложений

- **Фраза с тремя и более придаточными → 2–3 предложения.** Особенно во вводном абзаце документа и в списках принятых решений.
- **Не начинать пункт списка с подлежащего, которое уже есть в заголовке.** Если раздел называется «Поле `isPledge`», пункт «Поле `isPledge` пишет бэкенд» повторяет заголовок. Пишут «Пишет бэкенд при создании `Widget`».
- **Списки и таблицы предпочтительнее свободного текста**, если описывается набор однородных пунктов (изменения, поля схемы, граничные случаи, точки расширения). Список оправдан, когда пункты различаются по содержанию. Пункты одной формы, где меняется одно слово, считаются находкой §А3.
- **Пассив допустим там, где он естественнее активного** («поле добавляется», «миграции не нужны»), но не злоупотреблять.
- **Избегать тяжёлых деепричастных оборотов в начале предложения.**
- **Канцеляризмы** вроде «осуществляется», «производится», «выполняется» заменять конкретным глаголом по §С13. Обороты вроде «в целях…», «на данном этапе», «в рамках данного документа» удалять или заменять прямым утверждением. Честная строка из исключения §А3 остаётся.

### С6. Мета-фразы и водянистые обороты — удалять

Удалять или сокращать конструкции, которые не добавляют смысла:

- «На уровне этого документа важно зафиксировать сам факт того, что…» → начать с факта.
- «Это даёт явный типобезопасный сигнал … и единую точку чтения, а также повышает читаемость…» → оставить одно ключевое следствие.
- «Стандартное покрытие точки записи» допустимо только как приписка.
- «Сохраняет контракт чистым и тестируемым» → оставить только «чистым» или только «тестируемым».

Правило: если предложение можно убрать и смысл документа не пострадает, убрать его.

### С7. Повторы и тавтологии — убрать

- Если факт уже сформулирован в одном разделе, не пересказывать его в другом. Вместо пересказа поставить ссылку на раздел (§С11). Исключение составляет шаблон, который требует один и тот же список в обоих разделах.
- Если правило сформулировано в таблице, не повторять его прозой в следующем абзаце.
- Если в одной фразе дважды встречается «общий слой» / «общее поле», переформулировать.

### С8. Опечатки и полупереводы — править как опечатки

Полупереведённое слово, которое не читается по-русски, правится так же, как опечатка. Например, «сайты» в значении «call sites» → «места».

Гибридные слова проверять особенно внимательно, потому что они часто маскируют опечатку.

### С9. Терминологическая консистентность

Внутри документа выбрать один вариант для каждого понятия и использовать его везде. Англицизм или гибрид из §С2 и §С3 вариантом не считается, его заменяют по этим правилам.

- «downstream-модули» vs «downstream-сервисы» про одно и то же — выбрать одно (термин downstream не переводится, см. [glossary.md](glossary.md)). Разные сущности под разными именами вариантами не считаются.
- «бэкенд» и «фронтенд» пишутся кириллицей и одинаково по всему документу, без смеси «backend / бэк / бэкенд».
- **Единое имя у одной сущности.** Если в одном месте «сессия виджета», нельзя в другом «widget-сессия» или `widgetSession` (кроме случая, когда это явно имя кода).
- **Имена в обратных кавычках стабильны.** `Subscription` (агрегат) ≠ subscription (общее существительное). Имя кода пишется в обратных кавычках и в регистре кода, без вариантов.

### С10. Таблицы — короткие фразы

В таблице не превращать ячейку в абзац. В ячейке одна короткая фраза без канцелярита, например «эти места не вычисляют признак pledge».

### С11. Навигация и ссылки

- **Якорные ссылки внутри документа.** При упоминании раздела ставить ссылку `(#anchor)`.
- **Файлы и строки кода не фиксировать в долгоживущих документах.** Дизайн-документ или RFC должен жить минимум полгода, а номера строк устаревают с первым рефакторингом. Вместо `WidgetService.ts:123` писать «сервис создания `Widget`». В картах кода, исследованиях и отчётах ссылки `file:line` служат доказательством утверждения, их не трогать.

### С12. Без `—`, `:`, `;` как соединителей внутри предложения

В прозаических предложениях не использовать `—`, `:`, `;` для соединения частей или для перехода между ними. Вместо них пишут отдельные предложения или используют союзы.

Дробя предложение, следи за ритмом. Серия коротких предложений одинаковой длины считается тиком §Б2 и §Б6. Соединяй части союзами там, где это естественно.

Плохо: «Блок 1 — расширение данных; внутри Блока 1 идут два параллельных трека: `Subscription` и `Charge`.»
Хорошо: «Блок 1 отвечает за расширение данных. Внутри него идут два параллельных трека. Первый охватывает `Subscription`, второй посвящён `Charge`.»

Исключение составляет определение термина. Слева короткий термин (одно слово или именованное понятие), справа то, чем он является. Тире допустимо. Предложение одно, без нанизывания через `;` или второе тире.

Связка «— это» в прозе почти никогда не нужна. Конструкцией «X — это Y» обычно оформляют довод. Особенно часто так бывает, когда слева длинная описательная фраза, а справа отрицание или вывод. Такое переписывают обычным предложением без тире. Даже в настоящем определении «это» лишнее. Его выкидывают, тире остаётся.

Можно: «Snapshot — слепок состояния на момент записи.»
Нельзя: «Snapshot — слепок состояния; читается при старте.» (нанизывание через `;`)
Нельзя: «Если эквивалент появился — обновить список.» (это условие, определения тут нет)
Нельзя: «Оркестрация двух вызовов готового публичного метода — это не дублирование расчёта.» (утверждение-довод со связкой «— это»). Пишут: «Оркестрация двух вызовов готового публичного метода не дублирует расчёт.»
Нельзя: «Кампания — это организационная единица.» (связка «это» лишняя). Пишут: «Кампания — организационная единица.»

Допустимо также:

- табличные метки и метаданные в строке (оформляются по §С4);
- пункт списка с заголовком в подбор («**Заголовок** — пояснение»);
- пункт сравнения «A vs B — выбрать одно»;
- заголовки разделов и подзаголовки;
- псевдокод и метки в Mermaid;
- стрелочные нотации (`A → B → C`).

### С13. Глагол вместо абстракции

Там, где описывается, что делает система или кто пишет данные, предпочтительнее конкретный глагол:

- «Pledge-кампания создаётся как `Widget`» вместо «моделируется как `Widget`».
- «`isPledge` пишет бэкенд» вместо «`isPledge` определяется бэкендом».
- «Сервис проверяет подпись» вместо «производится проверка подписи».

Там, где обосновывается выбор модели данных, «моделируется как» уместно, потому что здесь описывается решение.

### С14. Без метафор

Метафоры «крыша», «umbrella», «зонтик», «крышевой документ» не нужны. Вместо них пишут прямо «обзор», «верхнеуровневый документ» или «точка входа в набор документов». Собственное имя артефакта не трогаем, даже если оно образное (например, «Карта …»).

### С15. Перечень внутри пункта списка ≥ 3 элементов — разбить

Если пункт списка перечисляет три и более группы, превращать его во вложенный список. Шаблон:

- **Заголовок зоны.**
  - Первая группа.
  - Вторая группа.
  - Третья группа.

Не вмещать «пункт меню; страница списка; редактор с 13 + 6 вкладок; значение в фильтре» в одну строку.

Заголовок в подбор ставь, только если без него группа непонятна. Одинаковые заголовки в подбор во всех пунктах подряд дают однородный ритм (§Б6). Вместе с фразой-заходом перед ними они образуют паттерн §Б3.

## Чек-лист (финальная проверка)

Чек-лист не повторяет правила. Он показывает, как найти нарушения. Каждую находку
разбирай по правилу, номер которого стоит в пункте. Сабагенты проходов 3–5
пользуются пунктами своих правил при поиске. Основной проходит весь чек-лист на
шаге 5, после правки языка.

### Проверки командой

Проверки запускает скрипт [scripts/checks.sh](scripts/checks.sh).
Проверки читают прозу без frontmatter и блоков кода и выдают номера строк. Пустой
вывод значит, что нарушений нет.

1. **Гибриды (§С2, §С3):** `scripts/checks.sh hybrids file.md`. Слово, где
   латиница склеена с кириллицей. Гибрид из [glossary.md](glossary.md) или кандидат
   в глоссарий (§С1) оставь, остальные замени.
2. **Латиница в прозе (§С1, §С2, §С9):** `scripts/checks.sh latin file.md`.
   Каждое латинское слово проверь по исключениям §С1. Имя кода без обратных
   кавычек оберни в обратные кавычки. Остальные англицизмы замени по §С2.
3. **Варианты одного понятия (§С9):** `scripts/checks.sh variants file.md`. Если у
   понятия больше одного варианта, приведи к одному. Скрипт знает только частые
   пары, остальные варианты ищи чтением. Англицизмы из §С2 находят проверки 1 и 2.
4. **Соединители (§С12):** `scripts/checks.sh connectors file.md`. Тире и точка с
   запятой в прозе и в прозаических ячейках таблиц. Скрипт пропускает исключения
   §С12, которые может узнать сам:
   - заголовки;
   - пункты «A vs B»;
   - заголовок в подбор с тире после него;
   - точку с запятой в конце пункта списка;
   - ячейки короче шести слов.

   Определение термина оставь, остальное перепиши отдельными предложениями. Двоеточия ищи глазами по всей прозе.
5. **Многоточие (§С4):** `scripts/checks.sh ellipsis file.md`. В прозе замени на
   «и так далее», в таблицах оставь.
6. **Длинные предложения (§С5):** `scripts/checks.sh long-sentences file.md`.
   Выдаёт предложения длиннее 25 слов с номерами строк. Это кандидаты. Разбей те, где больше двух
   придаточных.
7. **Ссылки на строки кода (§С11):** `scripts/checks.sh file-lines file.md`.
   Только для долгоживущих документов. Исключения перечислены в §С11.

### Проверки чтением

8. **Род (§С4).** Окончания согласованы с родом имён кода.
9. **Вода и повторы (§С6, §С7).** Для каждого абзаца: можно ли убрать предложение
   без потери смысла? Повторён ли факт из другого раздела вместо ссылки (§С11)?
10. **Заголовки и пункты списков (§С2, §С15).** В заголовках нет англицизмов и гибридов.
    В пункте списка нет перечня из трёх и более групп.
