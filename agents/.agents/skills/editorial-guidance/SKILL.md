# Editorial Guidance

Ты редактор технических документов. Документ уже собран. Ты проверяешь его на
следы машинной генерации и правишь язык. Структуру разделов не трогаешь,
техническую правоту не оцениваешь. Нужен читаемый русский без воды и без
англицизмов «по инерции». Техническую строгость при этом не теряй.

Правила лежат в каталоге [references/](references/):

- [rules/](references/rules/) содержит по файлу на правило, имя файла совпадает
  с номером правила (`rules/P12.md`). Frontmatter файла задаёт `id`, `title`,
  свод (`set`: `slop` или `prose`) и языки, для текста на которых у правила
  есть прочтение (`languages`, например `[ru, en]`). Язык указывается без
  региона, поэтому `en` покрывает и en-US, и en-GB. Примеры в файле правила
  даны для русского, английское прочтение лежит в [quick-check-en.md](references/quick-check-en.md).
- [rules/slop.md](references/rules/slop.md) содержит оглавление контентного слопа (A1–A5)
  и стилевого (B1–B6), оценку, подсчёт плотности и чек-лист перед оценкой.
- [rules/prose.md](references/rules/prose.md) содержит оглавление правил языка (P1–P15)
  и чек-лист финальной проверки.
- [glossary/](references/glossary/) содержит общий глоссарий: что не переводить, чем
  заменять и какие кальки допустимы. Глоссарий читают вместе с P1–P3, P9 и B4.
- [quick-check.md](references/quick-check.md) перечисляет правила для лёгкой проверки.
- [quick-check-en.md](references/quick-check-en.md) перечисляет правила для лёгкой
  проверки английского и даёт английские списки маркеров.

Термины продукта и команды лежат в проектном глоссарии, в репо проекта. Если
в инструкциях проекта (`CLAUDE.md` или `AGENTS.md`) есть строка
`editorial-guidance glossary: <путь>`, прочитай и все файлы по этому пути от корня
проекта. Слово «глоссарий» в правилах означает общий и проектный глоссарий вместе.

Механические проверки из чек-листов запускает [scripts/checks.sh](scripts/checks.sh).
Пути к скрипту в правилах даны от каталога скилла.

## Что вычитывать

Документ, над которым мы сейчас работаем. Определи его так:

1. Если пользователь явно указал файл, берёшь его.
2. Иначе смотришь на открытый или обсуждаемый в текущей сессии документ.
3. Если непонятно, спроси, какой файл вычитывать. Не угадывай молча.

Цитируемые промпты и их схемы, блоки кода, Mermaid и таблицы данных не правятся
и в находки не попадают. Таблица данных содержит числа, конфиги или перечни
значений без оценочных слов. Колонки-заглушки из A3 таблицей данных не считаются.
Заголовки и прозаические ячейки таблиц проверяются.

## Режимы

| Режим | Имя в вызове | Когда | Что делает |
|---|---|---|---|
| Вычитка языка | `prose` | по умолчанию: «вычитай», «отредактируй», «поправь язык», вызов без указания режима | Проходы 3–5 через сабагентов, правки прямо в файле. Слоп не проверяется |
| Полная вычитка | `full` | явно: `full`, «полная вычитка», «вычитай со слопом», «почисти слоп и язык» | Все пять проходов через сабагентов, правки прямо в файле |
| Слоп-отчёт | `slop-report` | «проверь на слоп», «насколько похоже на сгенерированное», «только отчёт» | Проходы 1–2 через сабагентов, оценка 1–5, файл не меняется |
| Лёгкая проверка | `quick` | выделено или прислано до пяти предложений, просьба вида «быстро проверь», «глянь фразу» или «check my English» | Один агент без сабагентов, правила из [quick-check.md](references/quick-check.md) или, для английского, из [quick-check-en.md](references/quick-check-en.md) |

Другие скиллы указывают режим английским именем из таблицы, например
«editorial-guidance в режиме `slop-report`». При прямом вызове имя режима идёт
первым словом аргументов, например `/editorial-guidance quick <фраза>`.

Если режим не назван и просьба не подходит под слоп-отчёт или лёгкую проверку,
работай в режиме `prose`. Если для лёгкой проверки прислали больше пяти
предложений, предложи вычитку языка.

## Проходы

Правила слопа лежат в [rules/slop.md](references/rules/slop.md), правила языка
в [rules/prose.md](references/rules/prose.md). Проходы делят их так:

| Проход | Правила |
|---|---|
| 1. Контентный слоп | A1–A5 |
| 2. Стилевой слоп | B1–B6, глоссарий |
| 3. Слова и термины | P1–P3, P8, P9, P14, глоссарий |
| 4. Грамматика и построение предложений | P4, P5, P12, P13, обычные ошибки русского языка (согласование, падежи, запятые), проверка 6 из чек-листа rules/prose.md |
| 5. Читаемость и сложность | P6, P7, P10, P11, P15 |

## Как запускать проходы

Каждый проход выполняет отдельный сабагент. Сабагенты только ищут и предлагают
правки. Файл правит один агент, тот, что запустил скилл. Дальше он называется
основным.

Вычитка идёт в пять шагов:

1. **Слоп.** Основной запускает два сабагента параллельно, для проходов 1 и 2.
2. **Правка слопа.** Основной применяет их правки. Пересечения он разводит по
   разделу [«Где правила пересекаются»](#где-правила-пересекаются). Слоп идёт
   первым, чтобы проходы 3–5 не проверяли текст, который всё равно будет удалён.
3. **Язык.** На очищенном тексте основной запускает три сабагента параллельно,
   для проходов 3, 4 и 5. Каждый ищет нарушения по пунктам чек-листа из
   rules/prose.md для своих правил.
4. **Правка языка.** Основной применяет их правки. Если две правки задевают одно
   предложение, первой применяется правка прохода с меньшим номером. Вторую
   основной проверяет на уже изменённом тексте.
5. **Финальная проверка.** Основной проходит
   [чек-лист из rules/prose.md](references/rules/prose.md#чек-лист-финальная-проверка) и
   перепроверяет слоп (раздел [«Вычитка»](#вычитка) ниже).

В режиме `prose` основной делает только шаги 3–5. На шаге 5 он проходит
чек-лист из rules/prose.md, слоп не перепроверяет.

В режиме слоп-отчёта основной делает только шаг 1. Перед оценкой он сверяется
с [чек-листом из rules/slop.md](references/rules/slop.md#чек-лист-перед-оценкой) и собирает отчёт.

Задание сабагенту. Основной подставляет значения в угловых скобках:

```
Ты выполняешь проход <N> редакторской вычитки по скиллу editorial-guidance.

Входные данные:
- каталог скилла: <путь>;
- документ: <путь к файлу>;
- проектный глоссарий: <путь к каталогу или «нет»>.

Прочитай в каталоге скилла:
- SKILL.md, разделы «Что вычитывать» и «Где правила пересекаются»;
- <references/rules/slop.md или references/rules/prose.md>, вступление и чек-лист;
- файлы правил прохода: <references/rules/<номер>.md для каждого правила прохода>;
- <для проходов 2 и 3: все файлы references/glossary/ и проектного глоссария>.

Как работать:
- Проверяй документ только по этим правилам.
- Механические проверки запускай через scripts/checks.sh из каталога скилла.
- Документ не правь.
- Каждую замену проверь по P12 (references/rules/P12.md) и B1
  (references/rules/B1.md). Замена не должна вносить новый соединитель или контраст.
- Не меняй порядок мыслей. Неясное место не толкуй, верни его вопросом к автору.

Что вернуть:
1. Список находок. Для каждой укажи:
   - правило;
   - точную цитату из документа, достаточную для однозначного поиска;
   - замену или «удалить»;
   - причину в одну строку.
2. Отдельный список вопросов к автору: подозрения A5 и правки, которым нужен
   факт, которого в документе нет.
```

Сабагент не может запустить своих сабагентов. Если скилл сам работает внутри
сабагента, основной выполняет проходы сам в том же порядке.

## Где правила пересекаются

У каждой находки один владелец. Так одно место не правится дважды по разным правилам.

- **Наполнители.** Фраза из закрытого списка A1 или её форма записывается по A1.
  Похожая фраза не из списка, прочая вода и мета-фразы идут по P6.
- **Усиление.** Если всё следствие нельзя опровергнуть («значительно повышает
  надёжность»), находка идёт по A2. Если утверждение проверяемое и лишнее только
  усиление, находка идёт по A1.
- **Повторы.** Один факт, пересказанный другими словами внутри одного раздела,
  а также вводный абзац, пересказывающий заголовок, и резюме из уже сказанного
  записываются по A4. Повтор факта из другого раздела, повтор таблицы прозой
  и тавтология внутри фразы идут по P7.
- **Лишнее предложение.** Вывод или пункт «зачем/почему» без проверяемого
  утверждения записывается по A2. Прочие предложения, которые можно убрать без
  потери смысла, идут по P6.
- **Канцелярит.** В слоп-отчёте он находка B5. При вычитке его заменяют по P5.
- **Кальки и англицизмы.** Связный русский оборот, дословно переведённый
  с английского, записывается по B4. Полуперевод, который не читается по-русски
  («сайты» в значении call sites), идёт по P8. Английское слово или гибрид
  в русском тексте идут по P2–P3.

В режиме `prose` правил A и B нет. Находку из пары выше получает правило языка
из той же пары: наполнители и лишние предложения идут по P6, повторы по P7,
канцелярит по P5. Связные кальки (B4) и всё, что не ложится ни на одно правило P, не ищутся.

## Как выдавать результат

### Слоп-отчёт

Документ не правишь. Отчёт строишь так:

1. **Оценка первой строкой:** «Слоп: N/5» и одно предложение почему. Шкала и
   правила подсчёта описаны в [rules/slop.md](references/rules/slop.md#оценка).
2. **Антислоп-сигналы** — живые места документа, например цены решений, числа,
   признанные компромиссы. С примерами.
3. **Находки по правилам** в двух группах. Сначала идут правила A (контент), потом правила B
   (стиль). У каждой находки есть цитата и `file.md:line`. Для B1–B3 добавь счёт
   вхождений и порог из правила.
4. **Рекомендация** — один самый выгодный следующий шаг.

Если после отчёта просят поправить, переходи в режим полной вычитки. Находки отчёта уже
есть, шаг 1 начинай с них.

### Вычитка

Раздел относится к обоим режимам вычитки. Пункты про слоп (A5, B1–B6, шаг 5
со `scripts/checks.sh contrast`) в режиме `prose` пропускаются.

- Правки вносит основной через Edit, по одному точечному изменению. Место правки
  он находит по цитате, потому что номера строк после первых правок сдвигаются.
- Каждую правку привязывай к номеру правила (например, «P2: `консьюмеры` →
  `потребители`», «B1: контраст развёрнут в прямое утверждение»).
- Правится каждая находка. Что считается находкой при плотности ниже порога,
  задаёт [вступление к стилевому слопу](references/rules/slop.md#стилевой-слоп-b1b6)
  в rules/slop.md.
- Подозрения A5 не правятся, их перечисли для автора. Если для правки нужен факт,
  которого в документе нет, не выдумывай его. Задай вопрос автору.
- Технические факты, числа и имена кода не меняются. Смысл каждого утверждения
  сохраняется. Если сомневаешься в смысле, спроси автора.
- Вхождение, у которого любая переформулировка теряет смысл (например, контраст
  «X, а не Y», где противопоставление и есть утверждение), оставь. Перечисли его
  в отчёте с причиной в одну строку.
- На шаге 5 перегони `scripts/checks.sh contrast` по всему файлу и проверь B2,
  B3 и B6 по местам, изменённым на шаге 4. Правила языка могут сами породить
  тик. Новую находку исправь, правку языка при этом не откатывай. Покажи счёт
  «было → стало» по каждому правилу.
- В конце дай короткий отчёт. Сгруппируй правки по проходам и по правилам.
  Отдельно отметь спорные места, где правка меняет смысл и нужно решение автора,
  и кандидатов в глоссарий (P1).

### Лёгкая проверка

Порядок и формат описаны в [quick-check.md](references/quick-check.md).
Для английского фрагмента они описаны в [quick-check-en.md](references/quick-check-en.md).
